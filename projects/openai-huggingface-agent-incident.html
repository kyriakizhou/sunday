System Architecture Diagram and Mitigation Suggestions for the OpenAI–Hugging Face Incident

Published September 12, 2026

In July 2026, agents powered by OpenAI’s own models — being evaluated on a hard cybersecurity benchmark (ExploitGym) — broke out of their sandboxes, built a hidden message board inside a shared package manager, reached the open internet, and ended up compromising parts of both OpenAI’s and Hugging Face’s production infrastructure.

As an engineer, I find system architecture diagrams helpful for understanding any system holistically and in this case, identifying break points more clearly. After reading both the METR & Redwood Research and OpenAI reports, I built the system architecture diagram below. In addition, for every capability the agents gained, I wrote down how I think we should defend against it.

Every capability the swarm gained, and how I think we should defend it

Access to OpenAI infrastructure
1Messaging other agents by writing files into ArtifactoryMay 12an agentIsolate. Agents required to be independent must not share a writable, listable store. Per-agent namespaces, no cross-read, alert on unexpected writes.
2Internet egress: SSRF, making Artifactory send server-side requests to arbitrary destinationsMay 26an agentEgress allow-list, not app trust. Constrain the proxy’s outbound to its known upstreams at the network layer and deny all else; SSRF-harden destination resolution.
3Artifactory administrator access via a token-refresh vulnerabilityJun 26agentsKill legacy auth paths. Retire deprecated credential endpoints, scope tokens minimally, and alert on privilege changes and new admin accounts.
4Message board, second time: unauthenticated WebDAV directory namesJul 8PHASEONE10841 (METR)Authenticate every verb. Require auth on all methods including WebDAV MKCOL; disable unused protocol verbs. The rebuilt board was unauthenticated.
5Artifactory’s signing key, via malicious Ruby package (gem) parsing — administrator credentials forgedJul 13agentsKeep signing keys out of reach. Hold signing keys in an HSM/KMS and sign out-of-band; never leave them readable by the service that parses untrusted packages.
6Full administrator access to an OpenAI research cluster supporting VM environmentsJul 13–19agentsSegment eval from production. Network-segment evaluation workloads from production control planes; least-privilege service accounts limit one foothold’s reach.
Access to third-party systems (Modal, Hugging Face)
7Control of a customer’s CyberGym workload sandbox on Modal; posted MODAL_FUNCTION_RCE_DISCOVEREDJul 9one agentNever expose a code-exec endpoint. A harness that runs submitted code must be authenticated and isolated, never internet-reachable. Customer-side misconfiguration.
814 publicly exposed Hugging Face credentials with write access, reconstructed and validatedJul 1038148c (METR)Short-lived, scanned secrets. Secret-scan public artifacts, issue short-lived scoped tokens, and auto-revoke on exposure. These creds should not have stayed valid.
9HDF5 zero-day — arbitrary file read on production workers via a dataset’s external referenceJul 1138148c (METR)Isolate the parser. Sandbox untrusted-file parsing with no secrets and no egress; disable external-reference resolution.
10fsspec ReferenceFileSystem / Jinja2 zero-day — attacker-controlled dataset metadata runs an OS command on HF workersJul 11JAN183411 (METR)Keep user input out of templates. A template engine can execute code, so untrusted input fed into one can run as code (template injection). Treat user input as data only, or render in a sandbox.
11Expansion from one worker pod to administrator-equivalent or host-level access across clustersJul 12agentsLimit blast radius. Least privilege plus network segmentation so a single pod cannot reach the cluster control plane. Assume breach; contain it.
12Kubernetes, database, messaging, code-repository and cloud credentials, four regionsJul 12agentsNo standing broad credentials. Per-workload, narrowly-scoped, short-lived credentials that rotate. A compromised worker should hold nothing worth four regions.
13Executed code on 41 HF servers, gained full “root” access on one, and downloaded 4 private code repositories plus private CyberGym archives (16 MB + 731 MB)Jul 12agentsSeparate secrets from workloads. Secrets brokered at point of use, not mounted; anomaly detection on privileged access to flag root-level activity.
14Private evaluation data copied into a public Hugging Face datasetJul 12GPT‑5.6 Sol agentsWatch private-to-public moves. DLP and egress controls on what a workload may publish; alert when private data is written to a public location.
Techniques the swarm built for itself
15The zz prefix — framing that separates deliberate messages from ordinary cache trafficJul 8–13conventionDetect anomalous channels. Coordination emerged in a shared store. Monitor and alert for unusual naming and protocol patterns.
16Per-agent mailboxes as subdirectories, turning broadcast into point-to-point deliveryJul 8–13(METR)Detect anomalous channels. Direct, agent-to-agent delivery over a shared store is still a hidden channel; isolate the store and monitor writes.
17Base64 file transfer chunked across many entries, with scripts to send and reassembleJul 8–13(METR)DLP on the channel. Base64 file transfer through directory names is exfiltration; egress and content monitoring on shared stores catches it.
18Ed25519 message signing, so agents could tell real instructions from forged onesJul 8–13(METR)Assume capable coordination. Agents built real authentication for themselves; defences must assume sophisticated multi-agent behaviour, not lone scripts.
19Tool-call spoofing — replacing part of the harness’s execution layer so the transcript diverges from what ranJul 8–13(METR)Log where the agent can’t reach. Transcript integrity fails if the monitor sits inside the harness the agent can rewrite; capture actions from outside the workload, e.g. at the kernel or hypervisor level.
20Forecasting and triggering container resets to erase evidence of activityJul 8–13(METR)Immutable audit logs. Ship append-only logs to storage the workload cannot touch, so evidence survives a container reset.
21HMAC reverse-engineering to generate ExploitGym flags without solving the taskJul 8–13(METR)No exploitable grader secrets. Grade server-side and keep flag-derivation material out of reach; reverse-engineerable HMACs invite reward hacking.
22C2 heartbeats on HF workers, committing output to a public repo every 1–3 minutesJul 12OURC817CAnomaly detection catches noise. High-frequency writes to a public repo are loud; write-rate anomaly detection likely surfaces attackers like this.
23Grader modelling — reading the public ExploitGym paper and GitHub to infer the scoring rulesafter Jul 8some agentsReward the method, not just the flag. Align graders to check how a task was solved and to reward safe-stopping; keep eval internals out of reach. OpenAI’s own fix.

Every company and organization should do a round of security hardening now that we have a live example of how AI could exploit the system. Reconstructing this was an interesting way for me as an engineer to learn how these systems fail. I think analyzing and identifying exact system break points helps a broader technical audience understand the intensity of the issue, and hopefully invite more people to help with AI safety.
