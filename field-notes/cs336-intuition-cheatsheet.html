CS336 intuition + cheatsheet (2026 version)

A good tokenizer has:

  • Good compression rate (bytes per token) so encoded token sequence doesn’t get too long (because attention is quadratic)
  • Each token gets used fairly same amount of times (instead of some very hot tokens and a lot of dead ones)

⇒ BPE: (byte1, byte2) / (word1, word2) → token

  • Most multilingual tokenizers have 100k-200k distinct tokens

Compute: flops (floating point operations) required per parameter, per token, during a full training pass (forward + backward)

Memory: bytes / parameter during a full training pass (parameters, gradients, optimizer states) + activations etc.

Basics:

Nowadays, people tend to do mixed precision training:

  • bf16 for parameters, activations, and gradients
  • fp32 for optimizer states

Helpful Napkin Math:

  • FLOPS for forward pass is 2 * #tokens * #parameters, and it dominates all computation
  • Hardware FLOP/s depends on hardware and data type (custom optimization done for certain data types)
  • Model FLOPs Utilization (MFU)
    • mfu = actual_flop_per_second_measured_on_hardware / promised_flop_per_sec_by_spec
    • usually, mfu > 0.5 is pretty good (will be higher if matmuls dominate)

Why only 0.5 utilization:

  • Need to move all data from Memory to Accelerator / Compute
  • Memory bandwidth (bytes/s) matters
  • communication time = bytes / memory bandwidth, compute time = flops / hardware flop/s
  • Operation is memory bound: communication time > compute time; compute bound otherwise
  • alternate way to see this:
    • accelerator intensity: how much work can the accelerators do per byte transferred?
      • h100_accelerator_intensity = h100_flop_per_sec / h100_bytes_per_sec
    • arithmetic intensity: how much actual work per byte for this workload
      • arithmetic intensity = flops / bytes
    • memory bound: arithmetic intensity < accelerator intensity

Napkin math / rough approximation for FLOPs:

  • Forward pass: 2 * # data points * # parameters
  • Backward pass: 4 * # data points * # parameters
  • Total: 6 * … (good approximation for Transformers when context length isn’t too big, when context length is too big, you can context length ^ 2 that’s not in this accounting)

Key metrics of an llm:

  • flops
  • memory
  • number of parameters

Activation / memory checkpointing: only store post relu, recompute pre relu. Tradeoff compute for memory savings.

Optimizations driven by system:

  • use RMSNorm instead of LayerNorm
  • drop bias term for typical linear and normalization steps are okay
  • these are things that involve memory movement but dont give us more arithmetic expressiveness

A normal transformer MLP:

x: [D]
up projection:   D -> F
activation
down projection: F -> D
MLP(x) = W_down GELU(W_up x)

A gated MLP, like swiglu or geglu uses two upward projections:

gate: D -> F'
up:   D -> F'
multiply them elementwise
down: F' -> D
GatedMLP(x) = W_down( SiLU(W_gate x) * (W_up x) )

Since gated activations introduce another upward projection matrix, to keep the number of parameters consistent, researchers often make each matrix 2/3 of the size (used to be 2 matrices, now 3, thus 2/3)

By 2026 March, variants of dense transformer architecture:

  • normalization layer
    • not include in residual stream
    • RMSNorm than LayerNorm for system optimization reasons
  • activations
    • gated on top of every previous versions
  • serial or parallel attn + mlp layers
    • parallel is more optimized system wise cause can fuse some attn and mlp components like norm but is less expressive cause mlp layer doesn’t get to see immediate process info that attention just brought in from other tokens

RoPE:

  • Basic idea behind RoPE: when token i attends to token j, the attention score depends on i-j rather than absolute values of i and j
  • example 
    seq_len = 4    # four tokens / four positions
d_head  = 6    # each Q/K vector has six numbers

    Use sequence:

    pos 0: "the"
pos 1: "cat"
pos 2: "sat"
pos 3: "down"

    In RoPE, d_head = 6 means we split each Q/K vector into 3 coordinate pairs:

    dims 0,1 -> pair 0
dims 2,3 -> pair 1
dims 4,5 -> pair 2

    Real RoPE frequencies, with base = 10000, are:

    pair 0: 1 / 10000^(0/6) = 1
pair 1: 1 / 10000^(2/6) = 0.046416
pair 2: 1 / 10000^(4/6) = 0.002154

    So for pair p, the three rotation angles are:

    [p * 1, p * 0.046416, p * 0.002154] radians

    Now use toy 6D vectors. Pretend these are already Q/K vectors after projection:

    "the"  pos 0: [1.0, 0.0,  0.2,  0.1, -0.3,  0.4]
"cat"  pos 1: [0.8, 0.6,  0.0,  0.3,  0.5, -0.1]
"sat"  pos 2: [0.4, 0.9,  0.5, -0.2,  0.1,  0.2]
"down" pos 3: [1.0, 0.2, -0.1,  0.4,  0.3,  0.7]

    For each pair (a, b), RoPE applies:

    a' = a cos(angle) - b sin(angle)
b' = a sin(angle) + b cos(angle)

    Example for "cat" at position 1:

    pair 0: [0.8, 0.6], angle = 1 rad
cos = 0.5403, sin = 0.8415
out = [-0.0726, 0.9974]

pair 1: [0.0, 0.3], angle = 0.046416 rad
out = [-0.0139, 0.2997]

pair 2: [0.5, -0.1], angle = 0.002154 rad
out = [0.5002, -0.0989]

    So RoPE-positioned "cat" is:

    [-0.0726, 0.9974, -0.0139, 0.2997, 0.5002, -0.0989]

    Full rotated vectors:

    "the" pos 0:
    [1.0000, 0.0000, 0.2000, 0.1000, -0.3000, 0.4000]

    "cat" pos 1:
    [-0.0726, 0.9974, -0.0139, 0.2997, 0.5002, -0.0989]

    "sat" pos 2:
    [-0.9848, -0.0108, 0.5164, -0.1528, 0.0991, 0.2004]

    "down" pos 3:
    [-1.0182, -0.0569, -0.1546, 0.3822, 0.2955, 0.7019]

    Key thing: RoPE does not create a separate position embedding and add it.
